## 1. Prevent opening start DM / join modal if chat already exists in DB and move from global chats to active chats #360

**Platform:** all
**Area:** chat list — search results, "Start DM / Join Chat" modal

### Description

When searching for a user, starting a DM (or joining a chat) and then tapping that same search result again, the "Start DM / Join Chat" modal opens again even though the chat already exists in the database. It only happens when the chat did not exist at the time the search ran.

Two things compound here:

1. DM search results are keyed by the peer's **user UUID**, while the DM chat itself has its own **chat UUID**, so a plain `uuid` comparison never recognises the DM that was just created.
2. The search sections (`_localChats` / `_remoteChats`) are a snapshot taken when the query was typed. Nothing recomputes them after a join, so the newly created chat stays in the "Global chats" section even though it is now stored locally.

### Steps to reproduce

1. Open the chat list and search for a user you have never talked to.
2. Tap the user in "Global chats" and confirm with "Start DM".
3. Go back to the search results (the query is still there).
4. Tap the same user again.

### Expected

The chat opens, and the user moves from "Global chats" to the local "Chats" section.

### Actual

The "Start DM" modal opens again even though the chat exists in the database.

### Notes

Fix: resolve a search result to a local chat by uuid, DM member uuid and handle (so an existing DM is found), and recompute the search sections from the local chat list after a successful join, without a server round trip.

### Acceptance

- Tapping a search result whose chat already exists locally opens the chat, never the modal.
- After starting a DM or joining a chat, the result moves from "Global chats" to "Chats".
- No extra `/search/all` request is issued to refresh the list.

## 2. Turnstile modal opens already showing an error on Android #359

**Platform:** Android (not reproduced on desktop/web)
**Area:** onboarding — login / signup, Cloudflare Turnstile modal

### Description

On login/signup, the Turnstile modal opens with the error state already visible (red message plus a "Retry" action) without the user doing anything. A moment later the Cloudflare widget loads and the challenge can still be solved normally.

### Steps to reproduce

1. Open login (or signup) on Android.
2. Fill the form and press the action button to open the security check.
3. Watch the modal as it opens.

### Expected

The modal opens with a neutral loading state and only reports an error if the challenge actually fails.

### Actual

The error state (red status message + retry button) appears immediately on open, then disappears/becomes irrelevant once Cloudflare renders.

### Notes

No console log was captured. Likely causes: `NavigationDelegate.onWebResourceError` on the embedded WebView forwards failed subresource loads (typically the Turnstile script on a cold WebView) as challenge failures, and the widget can be rendered before the container has a size, which puts Cloudflare in its own error/retry state.

Fix: only the embedded page reports failures (Turnstile `error-callback`, or the script never loading), render only once the container is measurable, and auto-reset on the first transient error instead of bubbling it to the app.

### Acceptance

- Opening the security check on Android never shows an error before the user interacts.
- A real failure still surfaces the inline error with a working retry.
- Login and signup succeed on Android, desktop and web.
